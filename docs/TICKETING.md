# Requirements and ticket workflow

The [PRD](PRD.md) records the business goal, scope, cross-feature safety boundaries, and success measures. The [ADR](ADR.md) records architecture choices. Feature IDs, detailed requirements, and acceptance criteria live in one Markdown file per ticket:

- `docs/backlog/fr-<feature-id>-<slug>.md` is a draft for upcoming work. Refine it with the Product Owner before implementation; a feature entry alone is not ready to build.
- `docs/tickets/fr-<feature-id>-<slug>.md` is the detailed requirement for a selected ticket. Keep the FR ID when moving it from backlog. [Backlog order](backlog/README.md) records build sequence separately; historical GitHub Issue numbers are separate identifiers. Keep the file's requirements and acceptance criteria current as scope changes.
- Infrastructure or repository workflow work that is not a product feature uses `docs/tickets/chore-<slug>.md` so it does not consume an FR implementation number.

The local Markdown ticket is the single source of truth for build requirements, acceptance criteria, dependencies, accepted decisions, and build readiness. The GitHub Issue displays a synchronized copy of its full Markdown content for review. GitHub Issues also track ownership, labels, discussion, delivery status, and handover. The Issue automation block derives delivery state from merged PRs; a merged implementation PR sets Progress & Handover to Done and records the PR. Do not copy transient delivery status into the ticket. Issue discussion changes the spec only after the accepted decision is written into the local ticket. The Issue and ticket link to each other. When an active Issue already exists, preserve its number and update its requirements copy after changing the local ticket; a requirements edit or code push must not create another Issue. Record native sub-issues and blocking dependencies in GitHub where available.

GitHub Issues and PRs labeled `LEGACY` are retired history. The existing misspelled label `LAGECY` has the same meaning until renamed. Exclude either label from duplicate-ticket lookup, current handoff or implementation evidence, and readiness decisions; use such records only for historical context. A new ticket may reuse the FR ID but must link an active Issue and PR.

For a UI backlog draft, completed UX contracts, mockups, and validation are reference work, not customer acceptance or delivery selection. Keep the draft in `docs/backlog/` until the customer accepts proposed layouts and selects the feature for delivery; record the dated decision in the local draft and UX handoff. When work is selected, refine its backlog file into testable requirements and move it to `docs/tickets/fr-<feature-id>-<slug>.md` without changing its FR ID. Put `**GitHub Issue:** Pending ticket/UX PR merge` in the ticket. Before implementation, the ticket must identify dependencies, applicable UX/architecture references, acceptance criteria, and the synthetic-data and human-review boundaries it touches.

To reset a workflow test, preview `npm run ticket:reset -- FR-01 FR-02`, then add `--apply` to move selected tickets back to backlog, clear ticket metadata and UX references, remove linked design files and matching implementation plans, update document links, and clear standalone FR status lines from this guide. Empty plan directories, including the old `doc/implementation-plan/`, are pruned. Add `--close-issues` only when the linked GitHub Issues should also be closed. The reset preserves requirements and accepted decisions. Review the printed file list before applying; the command does not delete unrelated files.

## Automation and document updates

`Ticket links` validation, `Merge validated ticket or implementation`, and `Ticket Issue activity` are enabled. PRs without ticket metadata skip implementation checks, including browser E2E. Eligible ticket/UX PRs auto-merge after ticket validation. The Ticket links workflow enables auto-merge after implementation validation, tests, typecheck, formatting, build, and browser E2E pass; repository branch rules also apply. CI uploads the dated HTML E2E report even when the browser check fails. After an implementation PR merges to `main` or `codex/main-backup`, automation marks its linked Issue Done and records the merged PR in Progress & Handover. For a new ticket, after its ticket/UX PR merges, use `npm run ticket:create -- docs/tickets/<file>.md` to create the Issue and add the reciprocal ticket link; the command refuses an unmerged ticket and checks the ticket path and FR ID for an existing active Issue before creating one. Ambiguous matches stop for reconciliation. Story Issues receive both `type:story` and `role:dev` on creation or reuse, making them eligible for automated implementation planning. If the ticket already links an active Issue, edit the local requirement file and run `npm run ticket:sync -- docs/tickets/<file>.md` to update that same Issue after the edit is pushed. Do not open a replacement Issue. The Issue form is a fallback when the command is unavailable and carries the same story labels. The Issue workflow supports `main`, `codex/main-backup`, and branches under `test/`.


Ticket/UX and implementation PRs use `.github/pull_request_template.md`: set `Issue: Pending` and `Type: ticket/UX` for the handoff PR; use the resulting `Issue: #<number>` and `Type: implementation` for a build PR. Open non-draft PRs by default; use draft status only when explicitly requested. List changed documentation paths or `Documentation: No change: <reason>`. Enable implementation auto-merge when the PR is ready; required checks and branch rules govern the actual merge. After a handoff merge, create or reuse its Issue with `npm run ticket:create -- docs/tickets/<file>.md`. After implementation merge, automation sets Progress & Handover to Done and closes the linked Issue as completed.

In the same PR as a behavior change, update the local ticket for ticket-level scope. Update the PRD and affected tickets for product-level scope; update API, stack, test-command, or design documents when those contracts change. Reviewers verify documentation content manually. Before `bmad-build`, run `npm run ticket:preflight -- docs/tickets/<file>.md`, then read the ticket in full and inspect its linked Issue and PRs; if implementation is already in review, merged, or blocked, report the next action instead of repeating the build. On `main` and branches under `test/`, preflight skips only the merged ticket/UX PR requirement so the build flow can be tested with the local UX documents; the Issue link, legacy, implementation, and handover checks still apply. Other branches require the merged handoff. After an implementation PR merges, automation marks its linked Issue Done and closes it as completed. Revert PRs should link the affected ticket and Issue.

## Ticket creation flow

1. Move the backlog draft to a numbered local ticket; refine scope, dependencies, open questions, and testable acceptance criteria.
2. For UI work, complete and verify `DESIGN.md`, `EXPERIENCE.md`, and browser-viewable HTML mockups. Add their paths to the local ticket.
3. Commit the ticket and UX handoff on a task branch. Open one PR with `Issue: Pending` and `Type: ticket/UX`; after validation, auto-merge follows repository branch rules.
4. After the merge, run `npm run ticket:create -- docs/tickets/<file>.md` to create or reuse the GitHub Issue and link the merged ticket. Review the Issue and any link PR before implementation.

Implementation starts after the reviewed ticket and UX handoff are ready, the Issue exists, and the reciprocal link is on the default branch; `bmad-build` follows those approved requirements as a separate delivery flow.

## End-to-end feature delivery

`bmad do fr-<number>` keeps the existing ticket/UX PR merge and Issue creation flow. Once the Issue and linked ticket exist on the default branch, follow `.agents/skills/bmad/references/do-feature.md`: read the ticket and Issue, run `ticket:preflight`, create or reuse `implement/fr-<number>-<slug>`, prepare an implementation plan from `.agents/skills/bmad-build/plan-template.md`, and run `bmad-build` from that plan. After verification, commit, push, and open one non-draft implementation PR; the Ticket links workflow enables auto-merge after required checks pass. The Issue workflow sets the linked Issue to Done after merge. `.agents/skills/vercel-react-view-transitions/references/implementation.md` applies only to View Transitions work.

## Automated implementation planning

After a merged story ticket creates or reuses its Issue, that Issue receives `role:dev` alongside `type:story`. Run `npm run plan:issues` to prepare draft plans for eligible open Issues, or pass an Issue number to plan one. The command excludes `LEGACY` and `LAGECY`, requires the Issue's `ticket-path` marker and local ticket, and runs `ticket:preflight` before each plan. Existing plan files are skipped so a rerun does not overwrite human edits. A preflight failure stops the run; resolve the ticket state before retrying.

Each plan is written to `docs/implementation-plan/<issue-title-slug>.md` using `codex exec --model gpt-6-sol`. The installed CLI does not accept `--full-auto`; the command uses `approval_policy=never` and a workspace-write sandbox to avoid interactive prompts. It supplies the Issue body as context and directs Codex to read the local ticket as the authoritative requirements. Review the draft, including its open questions and test seams, before implementation. Planning does not mark an Issue accepted or start a build.
