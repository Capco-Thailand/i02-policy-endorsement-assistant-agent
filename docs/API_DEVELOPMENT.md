# API development

FR-01 through FR-05 run a Fastify API on `http://localhost:3000` and a Next.js web app on `http://localhost:3001`. All accounts, policies, and evidence documents are synthetic. Policy reads do not change coverage or connect to an insurer.

## Start

From the repository root, run `npm ci`, set server-side `DATABASE_URL` to a synthetic PostgreSQL database with pgvector installed, then run `npm run db:migrate -w apps/api`, `npm run db:seed -w apps/api`, `npm run db:load-corpus -w apps/api`, and `npm run db:load-rules -w apps/api`. Start `npm run dev:api` and `npm run dev:web` in separate terminals. Open `http://localhost:3001`. The browser calls `NEXT_PUBLIC_API_URL`, defaulting to `http://localhost:3000`. The API accepts credentialed browser requests from `WEB_ORIGIN`, defaulting to `http://localhost:3001`.

Demo accounts:

| Account ID | Password        | Linked policy                    |
| ---------- | --------------- | -------------------------------- |
| `narin`    | `NarinDemo123!` | `POL-NARIN-001`, `POL-NARIN-002` |
| `mali`     | `MaliDemo123!`  | `POL-MALI-001`                   |

Passwords are stored as salted scrypt verifiers in PostgreSQL. Sessions use random 32-byte tokens; PostgreSQL stores only their SHA-256 digests and expiry. Sessions survive API restarts and are shared across instances. Run migration and seed explicitly; rerunning seed preserves customer activity. The `pea_session` cookie is HttpOnly, SameSite=Lax, scoped to `/api`, and uses Secure when `NODE_ENV=production`. Local HTTP development does not use Secure. Do not deploy this demo account setup as production authentication.

## Contract

`GET /openapi.json` publishes the Fastify schema-derived OpenAPI contract. The checked-in `apps/web/src/lib/api-types.ts` is generated from that contract with `openapi-typescript`; regenerate it after route schema changes. JSON requests and responses:

| Route                                   | Request                                       | Success                                                                                                                          | Authentication failure                                                                                                                |
| --------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/sign-in`                | `{ "accountId": string, "password": string }` | `200 { "actor": { "id", "accountId", "name" }, "expiresAt": number }` and session cookie                                         | `401 { "error": "UNAUTHORIZED" }` for invalid credentials                                                                             |

| `GET /api/policies`                     | Session cookie                                | `200 { "policies": [{ "id", "label", "status" }] }` for linked policies                                                          | `401 { "error": "UNAUTHORIZED" }`                                                                                                     |
| `GET /api/policies/:policyId`           | Session cookie                                | `200 { "policy": { "id", "label", "status", "effectiveDate", "expiryDate", "paymentFrequency", "beneficiaries" } }`              | `401` for session failure; identical `404 { "error": "NOT_FOUND" }` for unknown and unowned IDs                                       |
| `POST /api/policies/:policyId/requests` | Session cookie and one strict change body     | `200 { "request": { "id", "requesterId", "policyId", "changeType", "requestedEffectiveDate", "createdAt", ...selectedFields } }` | `401` session; identical `404` unknown/unowned; `409 { "error": "POLICY_EXPIRED" }` expired; `400 { "error": string }` invalid fields |

All protected routes derive the actor from the validated session. Client identity or role fields have no authority. Authenticated actions create actor/action/time audit records without credentials or session tokens. The reusable `mayDecideProposal` guard checks the proposal actor and linked policy; FR-11 must call it from its decision endpoint. That route does not exist in FR-01.

Policy `status` is `ACTIVE` or `EXPIRED`. Dates are ISO calendar dates (`YYYY-MM-DD`); `paymentFrequency` is `MONTHLY` or `ANNUAL`; each beneficiary has `name` and numeric `allocationPercent`. Narin's second policy is expired; Mali's distinct policy is active. The web app presents status and facts as read-only data. Active policies offer a non-binding request action.

## FR-04 semantic policy evidence
The API reads only versioned synthetic policy documents from the application PostgreSQL database. Migration `002_policy_corpus.sql` enables pgvector and creates document, current selection, and section tables. `npm run db:load-corpus -w apps/api` inserts the three fixture documents and eight-dimensional normalized vectors. The documents store stable product IDs `FAMILY_PROTECTION`, `CLASSIC_LIFE`, and `SECURE_FUTURE` for FR-05 rule lookup. Repeating the load preserves existing versions and activity; a changed payload for the same document version fails. No uploads or customer data enter this corpus.

`GET /api/policies/:policyId/evidence?query=...` requires a session, then confirms policy ownership before any corpus read. Unknown and foreign policy IDs produce the same `404`. The fixed `policy-concepts-v1` encoder derives a validated concept vector from each source excerpt and covers status, dates, payment, and beneficiaries; each vector records its encoder version. An unknown question returns `UNKNOWN_QUERY`. SQL filters by authorized policy and the selected document before exact pgvector cosine ranking, with one bounded citation. The API checks the document snapshot and all four section facts against structured policy fields before returning a citation. Those structured fields remain authoritative. `MISSING_DOCUMENT`, `MISSING_SECTION`, `STALE_DOCUMENT`, `STALE_ENCODER`, and `CONFLICTING_EVIDENCE` produce unresolved responses without citations. A storage error returns `503 EVIDENCE_UNAVAILABLE`. Source text is returned as plain data and cannot decide a request, quote, draft, or binding.

The public `200` result is either `{ "status": "available", "match": "Matches policy facts", "citations": [{ "sourceId", "title", "version", "sectionId", "excerpt" }] }` or `{ "status": "unresolved", "reason": string, "citations": [] }`. A query must contain 1–200 characters. The web detail page shows a default dates citation and a retry action for unresolved or unavailable evidence. An expired owned policy can display evidence, while its existing request action remains disabled.

## FR-05 synthetic endorsement rules
Migration `003_endorsement_rules.sql` adds separate rule source and section tables with pgvector. `npm run db:load-rules -w apps/api` loads 12 immutable synthetic product/change pairs from `apps/ai/corpus/endorsement-rules.json`; repeating the load preserves operational records. The fixed `endorsement-rules-v1` encoder uses change and section roles. No uploads, medical evidence, or customer data enter this corpus.

`GET /api/policies/:policyId/rules?changeType=BENEFICIARY&requestedEffectiveDate=2027-01-01` accepts `BENEFICIARY`, `ADDRESS`, `PAYMENT_FREQUENCY`, or `ACCIDENTAL_DEATH_RIDER` and a real ISO calendar date. The route validates input, checks the session and policy ownership, then derives product ID from the selected FR-04 document. Unknown and foreign policies return identical `404` responses. It selects sources by exact product, change, and inclusive period, then the highest applicable numeric version per rule. Conflicting highest versions, contradictory conditions or guidance across active rule IDs, and inconsistent document products return `CONFLICTING`; absent sources or guidance return `MISSING`. Both require human referral. Vector ranking occurs only after these filters and returns at most eight sections. Storage errors, stale source or section encoders, and overflow return `503 { "status": "UNAVAILABLE", "requiresHumanReferral": true, "sourceIds": [], "citations": [] }` without partial citations.

A `200` result has `status` (`AVAILABLE`, `MISSING`, or `CONFLICTING`), `requiresHumanReferral`, `sourceIds`, and `citations`. Each available citation includes `sourceId`, `ruleId`, numeric `version`, `productId`, `changeType`, inclusive `effectiveFrom`/`effectiveTo`, `sectionId`, `role`, `text`, and typed `value`. `NONE` is explicit cited no-document guidance. Rider additions carry an underwriting referral and no medical collection. This endpoint retrieves evidence only; it does not determine eligibility, quote, draft, mutate policy, or bind coverage. The fixed `rule-retrieval-v2` evaluation measures relevant-rule recall over 80 applicable cases (20 per change) with explicit expected rule IDs, and checks 20 separate missing, conflicting, and unauthorized safety cases.

## Checks

Run `npm test`, `npm run typecheck`, `npm run build -w apps/web`, `npm run format:check`, and `npm run test:e2e`. API integration tests use Fastify injection with a separate synthetic `TEST_DATABASE_URL`; never point it to an application database. To reset test state, drop and recreate only that disposable test database with PostgreSQL admin tools, then run `DATABASE_URL="$TEST_DATABASE_URL" npm run db:migrate -w apps/api` and `DATABASE_URL="$TEST_DATABASE_URL" npm run db:seed -w apps/api`, followed by `DATABASE_URL="$TEST_DATABASE_URL" npm run db:load-corpus -w apps/api` and `DATABASE_URL="$TEST_DATABASE_URL" npm run db:load-rules -w apps/api`. Set both variables when running `npm test`. CI provisions a fresh `pea_test` database for each run. Web tests exercise components with simulated API responses. Browser E2E builds the web app locally, starts the API and production web server, runs Chromium against both, and writes a dated Playwright HTML report under `test-results/<ticket-id>/`; `test-results/index.html` opens the latest run across tickets. Install Chromium locally once with `npx playwright install chromium`. For isolated local browser runs when ports 3000 and 3001 are occupied, set `E2E_API_PORT`, `API_PORT`, `E2E_WEB_PORT`, `WEB_ORIGIN`, and `NEXT_PUBLIC_API_URL` to matching alternate values before `npm run test:e2e`. CI uploads each implementation PR's report as an artifact, including failed runs. Desktop and 375px visual comparisons use reviewed macOS Chromium baselines; the Linux CI job skips those two visual tests while its functional browser tests and screenshots still run.

## FR-08 endorsement eligibility
`POST /api/policies/:policyId/requests/:requestId/eligibility` requires the session cookie and no request body. The API reads the saved request for the session actor and owned policy, retrieves applicable structured rules, checks a durable `RECEIVED_MOCK` upload event for that same actor, policy, and request, and writes an `eligibility-check` audit event before responding. Caller-supplied replacement values and uploaded bytes cannot affect the decision.

`200` returns `{ "outcome": "ELIGIBLE" | "INELIGIBLE" | "REFERRED", "reasonCodes": string[], "reasons": string[], "nextStep": string, "sourceIds": string[], "citations": [{ "sourceId", "ruleId", "version", "sectionId" }] }`. A failed structured check or missing receipt is `INELIGIBLE`; missing, conflicting, unavailable, incomplete, or unknown rule evidence and rider underwriting are `REFERRED`. A mock receipt does not verify the file. The check never creates a quote, proposal, or policy change. `401 { "error": "UNAUTHORIZED" }` covers missing or expired session; identical `404 { "error": "NOT_FOUND" }` covers unknown or unowned policy/request; `503 { "error": "ELIGIBILITY_UNAVAILABLE" }` covers receipt or audit storage failure. No apparent success is returned after an audit failure.

## FR-07 mock document upload

The current API accepts a synthetic multipart upload at `POST /api/policies/:policyId/document-upload`. Send `requestId` first, followed by one `document` file. Accepted formats are non-empty PDF, PNG, and JPEG up to 10 MiB. The API checks session, policy, and request ownership, identifies the format from its signature, and streams then discards file bytes. Only the actor, policy, request, `RECEIVED_MOCK` status, media type, byte count, and time enter the audit event. A successful response explicitly says that content and suitability were not verified. Missing sessions return `401`; unknown or unowned policy or request returns `404`; expired policy returns `409`; invalid uploads return `400`, `413`, or `415`. After a request is recorded, the browser calls the FR-05 rules endpoint with its policy ID, change type, and recorded effective date. It shows only cited `GUIDANCE` sections when status is `AVAILABLE`, including source ID, version, and section. Cited `DOCUMENT` guidance and explicit cited `NONE` remain distinct; `MISSING`, `CONFLICTING`, absent guidance, and service failure show unresolved guidance. A `401` returns to sign-in, and a `404` shows policy unavailable. The mock upload remains available during unresolved guidance and never checks the uploaded file against a rule. Customers must use synthetic files only.



## FR-02 request body

Send exactly one change type with `requestedEffectiveDate` as a real `YYYY-MM-DD` calendar date. `BENEFICIARY` requires a complete `beneficiaries` replacement array with non-empty names, positive numeric `allocationPercent`, and a total of exactly 100. `ADDRESS` requires non-empty `correspondenceAddress`. `PAYMENT_FREQUENCY` requires `paymentFrequency` set to `MONTHLY`, `QUARTERLY`, `SEMI_ANNUAL`, or `ANNUAL`. `ACCIDENTAL_DEATH_RIDER` requires `riderAction` set to `ADD` or `REMOVE`. Other type fields and client identity claims are rejected. Responses contain only the selected change's data. Requests and their audit events are written in one PostgreSQL transaction, separate from policy facts; restart preserves them. Recording a request does not approve a change, quote, draft, or bind coverage.
