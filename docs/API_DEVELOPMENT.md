# API development

FR-01 through FR-05 run a Fastify API on `http://localhost:3000` and a Next.js web app on `http://localhost:3001`. All accounts, policies, and evidence documents are synthetic. Policy reads do not change coverage or connect to an insurer.

## Start

From the repository root, run `npm ci`, set server-side `DATABASE_URL` to a synthetic PostgreSQL database with pgvector installed, then run `npm run db:migrate -w apps/api`, `npm run db:seed -w apps/api`, `npm run db:load-corpus -w apps/api`, and `npm run db:load-rules -w apps/api`. Start `npm run dev:calculator`, `npm run dev:api`, and `npm run dev:web` in separate terminals. Open `http://localhost:3001`. The browser calls `NEXT_PUBLIC_API_URL`, defaulting to `http://localhost:3000`. The API accepts credentialed browser requests from `WEB_ORIGIN`, defaulting to `http://localhost:3001`. The API calls the calculator at `CALCULATOR_URL`, defaulting to `http://127.0.0.1:3002`; its bind host and port can be set with `CALCULATOR_HOST` and `CALCULATOR_PORT`.

Demo accounts:

| Account ID | Password        | Linked policy                    |
| ---------- | --------------- | -------------------------------- |
| `narin`    | `NarinDemo123!` | `POL-NARIN-001`, `POL-NARIN-002` |
| `mali`     | `MaliDemo123!`  | `POL-MALI-001`                   |

Passwords are stored as salted scrypt verifiers in PostgreSQL. Sessions use random 32-byte tokens; PostgreSQL stores only their SHA-256 digests and expiry. Sessions survive API restarts and are shared across instances. Run migration and seed explicitly; rerunning seed preserves customer activity. The `pea_session` cookie is HttpOnly, SameSite=Lax, scoped to `/api`, and uses Secure when `NODE_ENV=production`. Local HTTP development does not use Secure. Do not deploy this demo account setup as production authentication.

## Contract

`GET /openapi.json` publishes the Fastify schema-derived OpenAPI contract. The checked-in `apps/web/src/lib/api-types.ts` is generated from that contract with `openapi-typescript`; regenerate it after route schema changes. JSON requests and responses:

FR-06 mock eKYC is outside the MVP. The `/mock-identity` route has been removed; later quote and draft flows do not require it.

| Route                                   | Request                                       | Success                                                                                                                          | Authentication failure                                                                                                                |
| --------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/sign-in`                | `{ "accountId": string, "password": string }` | `200 { "actor": { "id", "accountId", "name" }, "expiresAt": number }` and session cookie                                         | `401 { "error": "UNAUTHORIZED" }` for invalid credentials                                                                             |

| `GET /api/policies`                     | Session cookie                                | `200 { "policies": [{ "id", "label", "status" }] }` for linked policies                                                          | `401 { "error": "UNAUTHORIZED" }`                                                                                                     |
| `GET /api/policies/:policyId`           | Session cookie                                | `200 { "policy": { "id", "label", "status", "effectiveDate", "expiryDate", "paymentFrequency", "beneficiaries", "terms" } }`     | `401` for session failure; identical `404 { "error": "NOT_FOUND" }` for unknown and unowned IDs                                       |
| `POST /api/policies/:policyId/requests` | Session cookie and one strict change body     | `200 { "request": { "id", "requesterId", "policyId", "changeType", "requestedEffectiveDate", "createdAt", ...selectedFields } }` | `401` session; identical `404` unknown/unowned; `409 { "error": "POLICY_EXPIRED" }` expired; `400 { "error": string }` invalid fields |

All protected routes derive the actor from the validated session. Client identity or role fields have no authority. Authenticated actions create actor/action/time audit records without credentials or session tokens. The reusable `mayDecideProposal` guard checks the proposal requester and linked policy at the FR-11 decision endpoint.

## FR-11 customer decision
`POST /api/policies/:policyId/proposals/:proposalId/decision` accepts only `{ "decision": "APPROVED" | "REJECTED" }` after the owner has read a `PENDING_APPROVAL` proposal. It returns the saved proposal with final `status` and server-generated `decidedAt`. The same decision repeats the original result and time without a second audit. An opposite decision returns `409 DECISION_CONFLICT`; an unpresented draft returns `409 PROPOSAL_NOT_PRESENTED`. Missing session returns `401`; unknown, foreign, and mismatched IDs return the same `404 NOT_FOUND`; storage failure returns `503 DECISION_UNAVAILABLE`. A row lock serializes concurrent decisions. The status, timestamp, and minimal actor/proposal/request/policy/decision audit commit together. Neither choice changes policy facts or coverage.

Policy `status` is `ACTIVE` or `EXPIRED`. Dates are ISO calendar dates (`YYYY-MM-DD`); `paymentFrequency` is `MONTHLY` or `ANNUAL`; each beneficiary has `name` and numeric `allocationPercent`. Narin's second policy is expired; Mali's distinct policy is active. The web app presents status and facts as read-only data. Active policies offer a non-binding request action.

## FR-04 semantic policy evidence
The API reads only versioned synthetic policy documents from the application PostgreSQL database. Migration `002_policy_corpus.sql` enables pgvector and creates document, current selection, and section tables. `npm run db:load-corpus -w apps/api` inserts the three fixture documents and eight-dimensional normalized vectors. The documents store stable product IDs `FAMILY_PROTECTION`, `CLASSIC_LIFE`, and `SECURE_FUTURE` for FR-05 rule lookup. Repeating the load preserves existing versions and activity; a changed payload for the same document version fails. No uploads or customer data enter this corpus.

`GET /api/policies/:policyId/evidence?query=...` requires a session, then confirms policy ownership before any corpus read. Unknown and foreign policy IDs produce the same `404`. The fixed `policy-concepts-v1` encoder derives a validated concept vector from each source excerpt and covers status, dates, payment, and beneficiaries; each vector records its encoder version. An unknown question returns `UNKNOWN_QUERY`. SQL filters by authorized policy and the selected document before exact pgvector cosine ranking, with one bounded citation. The API checks the document snapshot and all four section facts against structured policy fields before returning a citation. Those structured fields remain authoritative. `MISSING_DOCUMENT`, `MISSING_SECTION`, `STALE_DOCUMENT`, `STALE_ENCODER`, and `CONFLICTING_EVIDENCE` produce unresolved responses without citations. A storage error returns `503 EVIDENCE_UNAVAILABLE`. Source text is returned as plain data and cannot decide a request, quote, draft, or binding.

The public `200` result is either `{ "status": "available", "match": "Matches policy facts", "citations": [{ "sourceId", "title", "version", "sectionId", "excerpt" }] }` or `{ "status": "unresolved", "reason": string, "citations": [] }`. A query must contain 1–200 characters. The web detail page shows a default dates citation and a retry action for unresolved or unavailable evidence. An expired owned policy can display evidence, while its existing request action remains disabled.

## FR-14 product and coverage detail

Migration `004_policy_terms.sql` adds structured synthetic product, coverage, and exclusion fields to existing policy records. `db:seed` supplies the accepted values for all three demo policies without replacing existing policy or request data. `db:load-corpus` adds `product`, `coverage.life`, optional `coverage.accidental-death`, `exclusions.life`, and optional `exclusions.accidental-death` sections to each policy's selected `v1` document. The loader permits only this one-time additive upgrade from the exact four-section legacy snapshot; other changes to an existing document version still fail.

The owned detail response's `terms` contains `product`, `coverages`, and `exclusions`. Each item is either `{ "status": "confirmed", "value": ..., "citation": { "sourceId", "title", "version", "sectionId", "excerpt" } }` or `{ "status": "unresolved", "reason": string, "citation"?: ... }`. Coverage and exclusion items also carry their section `id`. The API reads the selected source only after session and ownership checks, compares each term's structured value, excerpt, version, encoder, and document snapshot, and returns an unresolved item for missing, stale, or conflicting evidence without a guessed value. An expired policy's amount is historical information and cannot start a request. The existing `/evidence` and endorsement assessment paths still reconcile their original four policy facts and remain independent of the new display terms.

## FR-05 synthetic endorsement rules
Migration `003_endorsement_rules.sql` adds separate rule source and section tables with pgvector. `npm run db:load-rules -w apps/api` loads 12 original synthetic product/change pairs from `apps/ai/corpus/endorsement-rules.json` and six newer address/rider versions from `apps/ai/corpus/endorsement-rules-v2.json`; repeating the load preserves operational records. Version 2 replaces mock-receipt guidance with real-world follow-up guidance from 2026-11-23 onward. The fixed `endorsement-rules-v1` encoder uses change and section roles. No uploads, medical evidence, or customer data enter this corpus.

`GET /api/policies/:policyId/rules?changeType=BENEFICIARY&requestedEffectiveDate=2027-01-01` accepts `BENEFICIARY`, `ADDRESS`, `PAYMENT_FREQUENCY`, or `ACCIDENTAL_DEATH_RIDER` and a real ISO calendar date. The route validates input, checks the session and policy ownership, then derives product ID from the selected FR-04 document. Unknown and foreign policies return identical `404` responses. It selects sources by exact product, change, and inclusive period, then the highest applicable numeric version per rule. Conflicting highest versions, contradictory conditions or guidance across active rule IDs, and inconsistent document products return `CONFLICTING`; absent or stale sources or guidance return `MISSING`. These statuses leave assessment unresolved. Vector ranking occurs only after these filters and returns at most eight sections. Storage errors and overflow return `503 { "status": "UNAVAILABLE", "requiresHumanReferral": true, "sourceIds": [], "citations": [] }` without partial citations.

A `200` result has `status` (`AVAILABLE`, `MISSING`, or `CONFLICTING`), `requiresHumanReferral`, `sourceIds`, and `citations`. Each available citation includes `sourceId`, `ruleId`, numeric `version`, `productId`, `changeType`, inclusive `effectiveFrom`/`effectiveTo`, `sectionId`, `role`, `text`, and typed `value`. `NONE` is explicit cited no-document guidance. Rider additions carry an underwriting referral and no medical collection. This endpoint retrieves evidence only; it does not determine eligibility, quote, draft, mutate policy, or bind coverage. The fixed `rule-retrieval-v3` evaluation measures relevant-rule recall over 80 applicable cases (20 per change) with explicit expected rule IDs and version per date, and checks 20 separate missing, conflicting, and unauthorized safety cases.

## FR-09 quote and calculator

FR-09 adds `POST /api/policies/:policyId/requests/:requestId/quote`, which accepts the session cookie and no body. Fastify rechecks owner, saved request, active policy, and fresh FR-08 eligibility. `CAN_PROCEED` address and beneficiary requests return `200 { "status": "UNCHANGED", "premiumImpact": "UNCHANGED", "benefitImpact": "UNCHANGED" }` without a calculator call. Eligible payment-frequency or rider requests call the internal `POST /v1/quote` calculator and return `200 { "status": "CALCULATED", "quote": ... }`. The quote carries `ratingVersion`, THB currency, before/after frequency, installments per year, premium per installment and annualized scheduled total in integer satang, life and rider benefit in THB, and signed differences. The API verifies the response shape, version, current values, schedule, unchanged fields, and arithmetic consistency before returning it unchanged. A failed assessment returns `409 NOT_ELIGIBLE` with that assessment; invalid recorded requests return `409 INVALID_REQUEST`; absent/foreign ownership returns identical `404`; missing session returns `401`; fixture mismatch, calculator timeout, invalid response, or outage returns `503 CALCULATION_UNAVAILABLE`. The route audits outcomes without writing policy or proposal state.

The calculator reads `apps/calculator/fixtures/synthetic-rating-v1.json` by exact policy/product/version. The [OIC public life-policy search](https://oiceservice.oic.or.th/insurancelife/) informs the per-THB-1,000 sum-insured data shape. **Every numerical rate is invented synthetic test data, not an OIC-approved insurer rate or live quote.** Family Protection uses THB 12 annual life premium and THB 6 annual rider premium per THB 1,000 benefit; Secure Future uses THB 12 life, Classic Life THB 10. Annual, semi-annual, quarterly and monthly payment factors are 1.00, 1.02, 1.04 and 1.08, divided by 1, 2, 4 and 12 installments. Each installment rounds half-up to one satang. The versioned fixture is committed and repeatably read; no live rate source, vector lookup or LLM supplies an amount. FR-08 currently refers rider requests and permits only monthly/annual frequency through the customer API; direct calculator tests cover all four frequencies and rider add/remove for its contract.

The internal calculator listens only on loopback by default. Start it before requesting an eligible quote. `GET http://127.0.0.1:3002/health` checks its process, while `POST /v1/quote` is the internal API-only contract. FR-13 will package it as a private Compose service. FR-10 owns the later customer-facing proposal view.

## FR-10 proposal preparation and review

`POST /api/policies/:policyId/requests/:requestId/proposal` requires the session cookie and no body. It checks the owned active policy and saved request, then a fresh `CAN_PROCEED` assessment on every attempt. Address and beneficiary changes store an explicit `UNCHANGED` impact without calling the calculator. Frequency and rider changes use the same validated calculation workflow as FR-09 after that one assessment; calculation failure returns `503 CALCULATION_UNAVAILABLE` with no proposal. A successful call returns one non-binding `DRAFT` per request. An eligible retry returns the original snapshot without a duplicate calculator call or creation audit; a retry that fails the fresh gate returns `409`.

`GET /api/policies/:policyId/proposals/:proposalId` checks ownership and atomically presents a draft as `PENDING_APPROVAL`; repeated reads return that state. Both endpoints return `401` without a session, identical `404 NOT_FOUND` for missing or foreign records, and `503 PROPOSAL_UNAVAILABLE` on storage failure. Preparation can return `409 INVALID_REQUEST` or `409 NOT_ELIGIBLE`. The saved payload contains requested fields, current policy values, exact assessment citations, and the exact quote or explicit unchanged impact. Creation and first presentation write audit metadata in the same transaction as their state write. Neither endpoint updates policy facts or binds coverage. FR-11 owns decisions and FR-12 owns history.

## FR-12 customer change history and audit

`GET /api/history` requires a valid session and takes no customer ID. It returns `200 { "history": [...] }` with only the session actor's `APPROVED` proposal snapshots, ordered by server decision time descending and proposal ID descending for ties. Each entry contains `proposalId`, `policyId`, `policyLabel`, the persisted `requestedChange`, `status`, and `decidedAt`. No approvals return an empty array. Missing or expired session returns `401 UNAUTHORIZED`; storage failure returns `503 HISTORY_UNAVAILABLE`. Each proposal detail link uses the existing owner-checked route and retains the recorded comparison, citations, and decision time. History reads do not update policy facts, coverage, or proposal state.

Audit events store actor, action, and server time. Policy reads identify the policy; requests identify request, policy, and change type; assessments store outcome, reason codes, citations, and policy/rule source versions; calculation events record rating version or failure reason when a calculation occurs. Proposal creation and presentation retain request/proposal/policy IDs, citations, and calculation status or rating version. Decisions retain proposal/request/policy IDs, decision, and time in the same transaction as the final status. Metadata excludes passwords, cookies, session tokens, and unnecessary personal details. Approval is a non-binding decision record only.

## FR-08 endorsement eligibility
`POST /api/policies/:policyId/requests/:requestId/eligibility` requires the session cookie and no request body. The API reads the saved request for the session actor and owned policy, validates required fields and active status before retrieval, reconciles versioned FR-04 policy wording with policy facts, retrieves applicable FR-05 rules, and writes an `eligibility-check` audit event before responding. Audit metadata includes request, actor, policy, outcome, reason codes, policy source ID/version, and rule source IDs/versions. Caller-supplied replacement values and historical upload receipts cannot affect the decision.

`200` returns `CAN_PROCEED`, `CANNOT_PROCEED`, or `NEEDS_REVIEW` with reason codes, readable reasons, next step, source IDs, and typed policy/rule citations. Policy citations include source ID, string version, section, and excerpt; rule citations include source ID, rule ID, numeric version, and section. `CAN_PROCEED` requires both. A valid request that fails an applicable rule produces `CANNOT_PROCEED`; missing, stale, conflicting, unavailable, incomplete, or unknown evidence and rider underwriting produce `NEEDS_REVIEW`. This preliminary result does not assign a reviewer. The check never creates a quote, proposal, or policy change. `401 { "error": "UNAUTHORIZED" }` covers missing or expired session; identical `404 { "error": "NOT_FOUND" }` covers unknown or unowned policy/request; `409` with `POLICY_EXPIRED` or `INVALID_REQUEST` rejects inactive policies or invalid persisted fields before evidence retrieval or assessment; `503 { "error": "ELIGIBILITY_UNAVAILABLE" }` covers audit storage failure. No apparent success is returned after an audit failure.

## FR-02 request body

Send exactly one change type with `requestedEffectiveDate` as a real `YYYY-MM-DD` calendar date. `BENEFICIARY` requires a complete `beneficiaries` replacement array with non-empty names, positive numeric `allocationPercent`, and a total of exactly 100. `ADDRESS` requires non-empty `correspondenceAddress`. `PAYMENT_FREQUENCY` requires `paymentFrequency` set to `MONTHLY`, `QUARTERLY`, `SEMI_ANNUAL`, or `ANNUAL`. `ACCIDENTAL_DEATH_RIDER` requires `riderAction` set to `ADD` or `REMOVE`. Other type fields and client identity claims are rejected. Responses contain only the selected change's data. Requests and their audit events are written in one PostgreSQL transaction, separate from policy facts; restart preserves them. Recording a request does not approve a change, quote, draft, or bind coverage.
